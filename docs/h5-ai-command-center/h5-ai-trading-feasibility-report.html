H5 AI Trading Command Center 深度可行性报告

验证对象：H5 Excel 交易系统、QuantDinger 框架、多 agent research、Binance/TradFi 数据与执行、风控资管。

看结论 看 MVP

结论：可做，而且值得做；但 10 分版本必须是“交易飞控系统”，不是“全自动赚钱机器”。

之前的设想大方向成立：QuantDinger 可以作为产品骨架，TradingAgents 可以作为多 agent 协作范式，H5 可以结构化为 StrategySpec + Scenario Planner + Risk Kernel + Execution Desk。基础版本可做到 8 分；要做到 10 分，必须进一步证明它能减少坏交易、控制最大亏损、沉淀复盘记忆，并持续生成可验证的改进候选。

本报告的核心判断：H5 的产品优势不是更快下单，而是更稳定地做到“看懂、推演、等待、认输、风控、复盘”。10 分价值不是让 AI 多下单，而是让系统每天帮你少做坏交易。

1.1 如何从 8 分可行升级到 10 分值得做

10 分不是功能扩张，而是价值闭环加深。

10/10 value
维度8 分可行10 分值得做验收证据
Research能收集和总结信息能形成有来源、反方观点、交易影响和过期提示的证据包source_evidence + decision_packet
H5 判断能打分和给信号能解释为什么等、为什么不做、哪里失效、最多亏多少scenario_plan + invalidation + max_loss
风控能设置止损和仓位能账户级降级、冻结、利润锁定、策略预算耗尽后停止risk_event + account_state
执行能生成 paper/order intent能处理过期、部分成交、撤单失败、异常冻结和审计追踪execution_event + reconciler
成长能写复盘能每周生成候选改进，并强制 backtest/paper/shadow 验证reflection_entry + promotion_gate
10 分产品的北极星指标不是信号数量，而是 Bad Trade Avoided、Max Loss Known、Risk Rejection Quality、Review-to-Improvement Conversion。也就是：少做坏交易、每单亏损可知、拒绝有质量、复盘能进化。

1. 之前设想逐条验证

这部分只回答一个问题：原来的想法能不能变成可运行产品。

Validated assumptions
设想判断证据 / 理由产品决策
QuantDinger 作为骨架成立它已有 AI 分析、Python 策略、回测、live execution、自托管部署、Agent Gateway 等完整闭环。深抄生命周期和模块关系，不照搬品牌与受限前端资产。
TradingAgents 多 agent 协作成立但降权多 agent research、Bull/Bear debate、Risk/Portfolio Manager 有价值，但其自身定位仍是研究框架。Agent 产出 Decision Packet，不直接下单。
H5 可以策略化成立中轴、Keltner/ATR、均线成本、2B、量价结构、评分、资金管理都能字段化。做 StrategySpec，不做单一指标脚本。
Keltner 能给信号需改写Keltner 是 EMA/ATR 波动通道，可辅助趋势/偏离/风险距离；单独触轨不应自动交易。定位为 volatility distance 和 regime feature。
TradingView 可回测部分成立Pine strategy 使用 broker emulator，适合快速验证规则，但不能证明真实成交、滑点、队列、API 延迟。Pine 是 P1 快速验证；严肃验证必须 Python + paper + shadow。
Binance 支撑 crypto 数据/执行成立Spot/Futures API 有 depth、trades、klines、ticker、签名交易端点和权限模型。P0 接 public data；P1 才小额 semi-auto；P2 才 live auto。
Binance 融入股票/贵金属/原油可分析，谨慎执行Binance Futures 有 TradFi perpetuals，但它们是衍生品，不是底层股票/商品所有权；tokenized securities 有地区和接口边界。P0/P1 做 watchlist + research + risk display，执行后置。
半自动/API 自动由前端下命令成立执行模式可产品化为 SIGNAL_ONLY / SEMI_AUTO / AUTO_API。前端授权 + 服务器策略状态 + Risk Kernel 三重门。
资管风控是核心强成立任何策略都会失效，唯一可控的是单笔亏损、日损、回撤、仓位、权限和停止机制。Risk Kernel 是 P0，不是后置增强。
全市场全自动第一版上线不成立数据权限、API 差异、paper/live 差异、合规、风控、执行状态复杂度太高。砍掉。第一版做可控 MVP。

2. 推荐产品架构

这不是愿景图，而是后续开发的主链路。

Buildable architecture
01Market Data Layer

Binance Spot/Futures 优先；TradFi 先 read-only。

02Research Desk

技术、新闻、宏观、盘口、反方、风险 agent。

03H5 StrategySpec

Excel 逻辑、周期、中轴、Keltner、评分字段化。

04Scenario Planner

A/B/C/D 路径推演；准备动作，不预测。

05Risk Kernel

确定性硬闸门；计算最大亏损和执行权限。

06Execution Desk

SIGNAL_ONLY、SEMI_AUTO、AUTO_API 分级。

必须分层

信号、风控、资金管理、执行、复盘要拆开。否则亏损后无法判断问题来自策略、仓位还是执行。

必须有状态机

策略状态从 draft 到 backtested、paper、shadow、semi_auto、live_locked。没有阶段证据，不允许升级。

必须留审计

每次信号、拒绝、降级、挂单草稿、撤单、止损都记录输入、版本、原因和责任主体。

3. H5 策略可行性

H5 可落地，但必须是证据系统，不是神秘指标系统。

StrategySpec

可字段化的 H5 核心

  • 中轴：`axis_tf`、`axis_basis`、`basis_slope`、`price_distance_to_axis`。
  • Keltner：`kc_len`、`atr_len`、`atr_mult`、`kc_position`、`kc_width_pct`。
  • 均线成本：`ma20/60/120`、`deduct_price`、`cluster_width_pct`、`bias_atr`。
  • 结构：`2B`、假突破、回踩、支撑阻力、区间位置。
  • 量价：成交额突变、努力-结果背离、收盘位置、波动扩张/收缩。

不能这样做

  • 不能把 Keltner 上轨突破写成直接买入。
  • 不能把 Wyckoff 相位识别当成高确定性标签。
  • 不能为了回测收益暴力优化中轴周期。
  • 不能让评分达标绕过风控。
  • 不能把“AI 判断看多”变成订单。
中轴必须随品种波动和交易时长变化。比如确认做日内，BTC/ETH 可能优先 5m/15m；股票/贵金属/原油需要结合交易时段、跳空风险和波动结构再定。中轴是分析尺度，不是固定宗教。
StrategySpec minimum: strategy_id, version, symbol, venue, market_type axis_tf, entry_tf, confirm_tf, holding_plan kc_len, atr_len, atr_mult, kc_position, kc_basis_slope ma_cost_fields, deduct_price_fields, structure_fields, turnover_fields scenario_plan: A/B/C/D with trigger, action, invalid_condition risk: risk_pct, max_daily_loss, min_reward_r, kill_switch, mode_allowed validation: pine_status, python_status, paper_status, shadow_status, live_status

核心原则：分析可以跨市场，执行必须按 venue 分层。

Data / API
通道可行性第一版做法风险

5. 风控与资管可行性

这是系统成败的硬核，不是辅助模块。

Risk Kernel

Risk Kernel 必须是确定性规则

LLM 可以给理由、证据、场景和建议，但不能修改风控参数，不能绕过单笔亏损、日亏损、连续亏损、仓位、杠杆、滑点、数据新鲜度和执行模式。

max_loss = abs(entry - stop) * qty * contract_value + fee + slippage_buffer allow_order = max_loss <= account_risk_budget and daily_loss_remaining > max_loss and position_after_order <= position_limit and data_fresh == true and execution_mode_allowed == true

两套资金管理模板

  • Account State Template：账户级状态机，normal / conservative / reduce_only / frozen。
  • Strategy Budget Template：策略级预算，试错次数、利润锁定、降级和阶段升级。
  • ATR 仓位：波动越大，仓位越小；ATR 只管波动，不判断方向。
  • 最终仓位：取风险预算、杠杆、流动性、相关性、交易所规则的最小值。

Agent 权限边界

角色允许禁止原因
Research Agent读取行情、新闻、盘口、链上；产出 Evidence下单、改风控、读密钥避免 prompt injection 变成资金风险。
Risk Officer计算、否决、降级、冻结、解释原因创建方向信号、下单风险官不能成为交易员。
Execution Agent生成 paper order 或授权后的 order draft绕过 Risk Kernel、自行改数量/止损执行只执行已批准意图。
Operator前端确认、切换模式、Kill Switch关闭审计、跳过 P0 风控人也不能绕过系统纪律。

6. 推荐 MVP 范围

先做能自用、能验证、能复盘的系统。

Go build

P0：必须做

  • H5 StrategySpec Editor。
  • Binance Spot/Futures public data。
  • Research Mission + Decision Packet。
  • Scenario Planner A/B/C/D。
  • Risk Kernel v0。
  • Signal Card + Paper Order Intent。
  • Audit Log。

P1：第二阶段

  • TradingView Pine Export。
  • Python Backtest Lab。
  • Shadow Mode。
  • Broker read-only adapter。
  • TradFi watchlist / research。
  • Notification / approval workflow。

P2：后置

  • Small-size semi-auto live。
  • Binance AUTO_API 白名单。
  • IBKR / Alpaca / MT5 live adapter。
  • Tokenized securities execution。
  • Multi-account portfolio risk。
  • Public strategy marketplace。
MVP 的正确目标不是“马上赚钱”，而是建立一套你能每天用的交易工作流：标的扫描 -> research -> H5 评分 -> 场景推演 -> 风控判定 -> 信号/paper -> 复盘。这个闭环跑通后，才谈真钱执行。

7. 最终开发决策

如果现在开动，应该这样开。

Decision

Go

可以进入原型和开发规划。第一版定位为 Stark 自用的 AI Trading Command Center：以 Binance crypto 数据为主通道，支持 H5 策略证据、场景推演、Risk Kernel、Signal/Paper、审计复盘。

No-Go

不要做“全自动交易机器人”、不要承诺收益、不要第一版接大资金实盘、不要把 tokenized stocks / TradFi perps 当成普通股票交易、不要让 LLM 直接下单。

开发前检查清单

检查项通过标准未通过动作
H5 Excel 规则结构化StrategySpec 字段能覆盖中轴、指标、评分、资金管理、执行模式继续拆 Excel，不写代码
Risk Kernel单笔最大亏损、日损、连续亏损、仓位、Kill Switch 可运行禁止任何 live adapter
Pine/Python 一致性同一 StrategySpec 可以导出 Pine 并在 Python 复刻只保留 research，不升级 paper
Paper / Shadow至少跑 2-4 周，记录风控拒绝、滑点估计、错过成交不允许 semi-auto
权限与审计所有 agent/action 有 scope、input_hash、reason、operator不允许 API key 接入
